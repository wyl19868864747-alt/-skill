# 林枫生图：学习成长系统

本系统把日常使用中的有效经验保存、验证和复用，同时防止一次随机失败、临时审美或单项目要求污染长期 Skill。

流程：`使用 → 观察 → 候选 → 验证 → 晋级 → 生效 → 复核 → 退役`。

## 学习证据与生效规则分离

- 学习证据记录发生了什么、如何修正、为什么有效以及是否复现；先进入 `learning-inbox.md`。
- 生效规则只有通过验证后才影响未来任务；未验证候选不得在新任务中执行。
- 稳定、跨模型的视觉逻辑进入 `visual-decision-principles.md`。
- 可能随模型、平台或工作流变化的经验进入 `active-learnings.md`。
- 专项执行标准进入对应 reference；只有路由、顺序或总流程变化才修改 `SKILL.md`。

## 学习触发器

只在以下情况形成候选：

- 用户指出错误并给出修正方向或因果解释；
- 同类失败在不同任务重复出现；
- 一项调整带来可观察、可复现的改善；
- 用户明确说“以后注意、作为原则、加入 Skill、可以复用”；
- 模型、平台或工作流出现可复现的能力变化。

不记录项目人名、品牌 brief、价格、文件名、单图坐标、私人信息、无原因的单次喜恶、不可归因的抽卡失败或已有规则的简单重复。

## Candidate 标准

每条候选使用 `LC-YYYYMMDD-XXX`，包含：日期、来源、任务类型、模型/平台、现象、用户修正、因果解释、候选规则、适用范围、例外、关联规则、证据数、独立任务数、置信度、状态、同步状态和证据备注。

相似反馈按语义合并到同一 Candidate：增加证据数；来自不同项目时增加独立任务数；只有因果机制不同才新建编号。

## 状态机

- `观察`：单次现象，因果仍不清楚。
- `候选`：因果与边界初步清楚，等待独立验证。
- `已验证`：至少两个独立任务得到同方向改善；或用户明确批准全局采用，且因果、范围与例外清楚。
- `生效`：已合并到正式执行层。
- `退役`：模型变化、新证据或替代规则使旧规则不再适用。
- `拒绝`：确认属于偶然、项目限定或错误归因。

## 晋级前防污染检查

逐项判断：

1. 是因果规律还是单次相关性？
2. 是否有独立任务验证，或用户明确批准全局采用？
3. 适用范围和例外是否明确？
4. 是否与已有规则重复或冲突？
5. 是否会覆盖用户本轮要求或已确认资产？
6. 是否会让简单任务无谓复杂化？
7. 是否值得永久维护成本？

关键问题无法回答时不晋级。

## 运行与持久化

- 任务开始只加载生效规则，不读取未验证候选。
- 用户即时修正先服务当前结果；记录不得打断当前任务或增加交付噪声。
- 只有用户明确要求保存经验、总结优化、更新 Skill 或已授权持续学习工作流时，才持久化 Candidate；普通调用不得假定 Skill 会自行改写。
- 本技能内 `learning-inbox.md` 是正式母版的候选队列和字段模板。若存在用户指定的外部持久化 Inbox，日常候选先写外部 Inbox，复盘时再合并进母版。

## 定期复盘与多账号合并

用户要求总结优化或同步母版时：收集未处理 Candidate，按语义去重，排除项目限定项，合并证据，决定继续观察、验证、晋级、拒绝或退役，更新对应规则与 `growth-ledger.md`，再标记同步状态。

不同账号和 Codex 只贡献带来源的 Observation、Candidate 与 Evidence；相同因果规则合并为一条。用户指定 GitHub `main` 为唯一权威母版后，所有正式晋级只进入该母版，调用端不得形成永久分叉。

每累计十条生效规则进行同义合并、冲突检查与退役清理；生图模型重大升级后优先复核所有模型相关 Active Learnings。
